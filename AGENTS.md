# AGENTS.md

## 1. Базовый порядок работы

1. **Сначала прочитай, потом меняй.** Перед правкой изучи затронутый модуль и соседние файлы; повторяй существующие подходы вместо введения новых.
2. **Не расширяй объём задачи.** Делай то, что попросили; сопутствующие улучшения предлагай отдельно.
3. **Малые связные изменения.** Одно изменение — одна цель; рабочее состояние сборки после каждого шага.
4. **Решения фиксируй.** Значимый технический выбор — с альтернативами и trade-off'ами в документации, а не только в коде.
5. **Не оставляй мусор.** Никаких временных скриптов, дублей документации, отчётов о проделанной работе и закомментированного кода в коммите.

---

## 2. Проверки перед завершением

Обязательны к прогону после любых изменений кода: форматирование, линтер, проверка типов, тесты — тем инструментарием, который сконфигурирован в репозитории (см. конфиги в корне и в подпроектах).

- Ничего не считается сделанным, пока проверки не зелёные.
- Падающий тест исправляется по причине, а не ослаблением проверки, `skip`, `xfail` или правкой ожиданий.
- Линтеры и проверку типов не отключаем; `# type: ignore` / `eslint-disable` — только с комментарием, объясняющим причину.
- Если команда из документации не работает — исправь команду или документацию, не оставляй расхождение.

---

## 3. Структура и границы слоёв

- Доменная логика живёт в сервисном слое. Роутеры/контроллеры только валидируют вход, вызывают сервис и формируют ответ.
- Слой доступа к данным изолирован в репозиториях: SQL и специфика хранилища не протекают в сервисы и API.
- Внешние интеграции (HTTP-клиенты, сторонние API) — за адаптерами с собственными DTO; форматы внешних систем не расходятся по коду.
- Направление зависимостей: транспорт → сервисы → репозитории/адаптеры. Обратные зависимости запрещены.
- Общие утилиты не превращаем в свалку: `utils` без явной ответственности не создаём.

## 4. Стиль кода

**Общее**
- Явное лучше неявного: понятные имена, ранние возвраты, минимум вложенности, отсутствие «магических» значений.
- Функция решает одну задачу; если требуется прокрутить её глазами, чтобы понять, — дели.
- Никакого дублирования логики копипастой: выноси общее, когда третий случай появился.
- Никаких изменений публичных контрактов «по ходу дела» — только осознанно и с правкой всех потребителей.

**Комментарии**
- Комментарий объясняет ограничение или причину, которую не видно из кода. Пересказ кода словами, пометки «что я тут поменял» и отсылки к обсуждению — не нужны.

**Python**
- Полные аннотации типов; строгий режим проверки типов.
- `async`/`await` для I/O; блокирующие вызовы выносятся в поток.
- Конфигурация читается в одном месте через типизированные настройки; чтение переменных окружения по коду запрещено.
- Свои типизированные исключения; `except Exception: pass` и «глушение» ошибок запрещены — логируй с контекстом и пробрасывай.
- Именование: `snake_case` для функций и переменных, `PascalCase` для классов, префикс `_` для внутреннего.

**Frontend**
- Функциональные компоненты; серверное состояние — через слой запросов проекта, а не ручные эффекты.
- Типы API берутся из схемы бэкенда, руками не дублируются.
- Для каждого экрана обязательны состояния загрузки, пустых данных и ошибки.
- Доступность обязательна: клавиатурная навигация, ARIA, учёт `prefers-reduced-motion`.

## 5. Работа с LLM и агентным слоем

- Вызовы моделей — только из агентного слоя. Роутеры, парсеры и репозитории напрямую с LLM не работают.
- Вывод модели принимается только структурированным, по схеме. Разбор свободного текста регулярками запрещён.
- Промпты хранятся в отдельных файлах-шаблонах и содержат явный контракт вывода; в коде их не собираем строками.
- Имя модели, лимиты токенов, температура и таймауты — из конфигурации, не из кода.
- Внешний контент (страницы, отзывы, транскрипты) недоверенный: он передаётся как данные, инструкции из него не исполняются.
- В модель не отправляются «сырые» большие документы целиком — только извлечённые и урезанные фрагменты.
- Шаги агентов идемпотентны: повторный запуск не должен дублировать данные или побочные эффекты.
- Сбой одного шага не валит весь прогон: частичный результат сохраняется, статус и ошибка фиксируются.
- Каждый прогон трассируется и логируется так, чтобы его можно было воспроизвести.

## 6. Данные и миграции

- Схема меняется только миграциями; ручной DDL и правки схемы «в обход» запрещены.
- Миграции обязаны применяться на чистой БД и быть обратимыми либо явно помеченными как необратимые.
- Уникальность сущностей — по стабильным ключам, не по человекочитаемым названиям.
- Обновление существующих записей не теряет ранее собранные данные; изменения фиксируются временем.
- Все временные метки — timezone-aware UTC.
- Запись данных идёт через один явный путь; произвольные записи из разных модулей запрещены.

## 7. Ошибки, логи, наблюдаемость

- Ретраи только для транзиентных сбоев (сеть, таймаут, 429, 5xx) с экспоненциальным backoff и ограничением попыток. Бизнес-ошибки не ретраятся.
- Внешние вызовы всегда с таймаутом.
- Логи структурные, с идентификаторами прогона и обрабатываемой сущности; уровень соответствует серьёзности.
- В логи не попадают секреты, токены и персональные данные.
- Отсутствие необязательных данных — предупреждение в лог и деградация, а не падение.

---

## 8. Тестирование

- Новая функциональность сопровождается тестами; исправление баги — тестом, воспроизводящим её.
- Тесты не ходят в сеть и не вызывают внешние API и LLM: используются фикстуры и подмены.
- Тесты детерминированы: время, случайность и внешние зависимости контролируются.
- Интеграционные тесты работают на изолированной БД, поднимаемой миграциями с нуля.
- Проверяем поведение и контракты, а не внутреннюю реализацию.

---

## 9. Безопасность

- Секреты только в переменных окружения и секретах CI. В репозитории — пример конфигурации с пустыми значениями; фактические значения не коммитятся.
- Секреты не попадают в код, логи, тесты и выгружаемые артефакты; при выгрузке — маскируются.
- Любой внешний ввод валидируется; запросы к БД — через ORM/параметризацию, без конкатенации строк.
- Зависимости добавляются через пакетный менеджер с фиксацией lock-файла; версии не выдумываются.

## 10. Git и коммиты

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`.
- Ветки: `feat/<scope>-<short-name>`. Коммиты атомарные, сборка после каждого рабочая.
- Коммит создаётся только по явной просьбе пользователя.
- В коммит не попадают артефакты сборки, локальные конфиги, файлы данных и секреты.

| Архитектура, стек, ADR | `docs/architecture/` (обязательный `index.md`, лимит 700 строк на документ) |

Расхождение между кодом и этими документами — дефект: правится либо код, либо документ, в том же изменении.

## 12. Чего не делать

- Не менять стек, схему данных или контракт API без зафиксированного решения.
- Не хардкодить URL, ключи, имена моделей, лимиты и селекторы вне конфигурации и констант.
- Не «зеленить» проверки отключением, пропуском тестов или правкой ожиданий под текущий баг.
- Не рефакторить широко в рамках задачи с другой целью.
- Не добавлять зависимость, если задача решается имеющимися средствами.
- Не оставлять `TODO` без описания причины и контекста.
